A field guide to retrieval-augmented generation

RAG is not one pattern. It is a family of choices across preparation, retrieval, reasoning, modality, architecture, and evaluation. This taxonomy organizes those choices by where they act in the system.

The canonical pipeline

Offline

build the index
1 · IngestBring in source documents and preserve provenance.
2 · ParseRecover headings, tables, images, and reading order.
3 · ChunkSplit into retrievable units without losing useful context.
4 · Embed + storeEncode chunks and write them to a searchable index.
→

Online

answer a question
1 · AskTurn the user question into one or more searches.
2 · RetrieveFind candidates; typically return 3–5 passages.
3 · AugmentCombine instructions, evidence, and the question.
4 · GenerateAnswer from grounded context and expose sources.

RAG addresses two core LLM limits: unsupported answers and knowledge frozen at training time. Updating the store changes the next retrieval without retraining the model.

Describe any RAG system in seven questions

Instead of asking only 'Which RAG type is this?', ask these seven questions. The first two shape the knowledge before any query is asked; the other five decide what happens when a query arrives.

Offline: build the knowledge

Knowledge representation

What structure is preserved in the searchable material?

  • Flat chunks
  • Structure-aware or context-enriched chunks
  • Parent-child hierarchy
  • Document tree
  • Entity-relationship graph

Knowledge access and lifecycle

Where does knowledge live and how is it maintained?

  • Indexed document collection
  • Multiple knowledge bases
  • Connected external sources
  • Incremental ingestion
  • Metadata, permissions, and lineage

Online: answer the query

Control flow

Who decides when, where, and how often to retrieve?

  • Single-pass pipeline
  • Fixed multi-stage pipeline
  • Agent-selected source or tool
  • Iterative or self-reflective loop

Retrieval signal

What makes evidence relevant enough to return?

  • Lexical matching
  • Embedding similarity
  • Sparse + dense fusion
  • Graph relationships
  • Reasoning over a document outline

Context assembly

What evidence is actually passed to the generator?

  • Selected passages
  • Expanded parent sections or documents
  • Ranked, merged, or compressed evidence
  • Metadata-filtered and permission-scoped context

Modality

What is searched, and what can the generator see?

  • Text only
  • Media converted to text
  • Text retrieval with original media
  • Aligned cross-modal embeddings with multimodal generation

Answer policy

What should the generator do with the evidence?

  • Refuse when evidence is insufficient
  • Ask for clarification
  • Present conflicting answers
  • Cite sources
  • Choose output format (text, chart, code)

Foundation

Start with the fixed contract: retrieve external evidence, place it beside the question, then generate. Everything else in the taxonomy changes how evidence is prepared, found, or used.

The RAG contract

Query time

The prompt contains three things: an instruction, retrieved content, and the user question. The model generates from this assembled context and can cite the evidence. The stack remains modular: vector store, embedding model, and LLM can be swapped independently.

AskRetrievalReturnAugmentationGeneration
Sources: WhatisRetrievalAugmentedGenerationRAG; MCPvsRAGHowAIAgentsLLMsConnecttoData; RAGvsCAGSolvingKnowledgeGapsinAIModels

Problems it is designed to solve

Query time
  • Unsupported answers: primary-source context makes claims checkable.
  • Stale knowledge: update the store instead of retraining the model.
  • False certainty: a grounded system can say “I don’t know” when the store has no answer.
  • Excessive refusal: weak retrieval can trigger too many “I don’t know” responses even when the answer exists in the source material.
Source: WhatisRetrievalAugmentedGenerationRAG

More context is not always better

Architecture

Adding retrieved tokens produces marginal accuracy gains, then can degrade performance through noise and redundancy. It also increases cost and wait time. The optimization target is signal, not volume.

Source: RAGvsAgenticAIHow LLMsConnectDataforSmarterAI

The evolution of RAG

Architecture
KeywordSparse retrieval has about 50 years of history; exact terms, inverted indices, TF-IDF/BM25.
SemanticDense retrieval is about 5 to 10 years old; embeddings add intent beyond exact wording.
HybridPractical deployments are about 2 to 3 years old; keyword precision plus semantic recall.
LLMsFluent generation, but no private or current knowledge.
Naive RAGOne retrieval pass augments one prompt.
AdvancedRerankers, rewrites, hybrid retrieval.
AgenticRetrieval becomes a decision inside reasoning.

Advanced RAG made retrieval smarter but left the pipeline predetermined. Agentic RAG decides whether retrieval is needed, where to search, what to ask, and when to stop. BM25 can outperform neural methods on domain-specific terms, so evolution does not mean sparse retrieval became obsolete.

02

Prepare knowledge

Index-time work determines the ceiling of retrieval quality. Preserve meaning, structure, permissions, and provenance before a query ever arrives.

Naive chunking

Index time

Fixed-size splits, paragraphs, sliding windows, or recursive rules. Cheap and easy, but headings can separate from their paragraphs and tables from their explanations.

Sources: WhatIsChunklessRAGHowDoclingAIAgentsNavigateDocuments; EveryRAGStrategyExplainedin13MinutesNoFluff

Context-aware chunking

Index time

Detect natural boundaries so splits preserve document structure rather than cutting every fixed number of characters. Docling’s hybrid chunking is the implementation named in the talk, which characterizes the approach as free and fast.

Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Late chunking

Index time

Embed the whole document first, then divide token embeddings so each chunk retains full-document context. It needs long-context embedding models and is described as the most complex strategy.

Experience caveat: the speaker had not used this approach at recording time.
Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Contextual retrieval

Index time

An LLM prepends a short description of how each chunk fits the document, separated from the chunk by “---”; the enriched text is embedded together. Promising gains, but an LLM touches every chunk.

GainLocal text retains its role in the whole.
CostSlower and more expensive indexing.
Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Hierarchical RAG

Index timeQuery time

Store parent–child relationships as metadata. Search small units such as paragraphs for precision, then return the larger parent for context: “searching small with context, returning big.”

Best whenThe parent document fits in context.
Trade-offMore complexity and some unpredictability.

Important distinctions

Editorial view: hierarchical retrieval does not inherently require an agent. Parent-child expansion is a representation and context-assembly choice; an agent may choose to use it. The transcript calls it “sort of a subset of agentic RAG.”
Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Document intelligence with Docling

Index time

Docling is an MIT-licensed Linux Foundation Data & AI project that converts PDFs, Word, PowerPoint, scanned images, and spreadsheets into structured Markdown, text, or JSON. Its hierarchical document model preserves headings, tables, reading order, and element-level provenance such as page and bounding box.

  • Structure-aware chunking keeps sections, tables, captions, titles, and headers connected.
  • Optional figure descriptions make visual elements retrievable.
  • Schema-based extraction can return validated fields such as invoice number and price.
  • Outputs integrate with LangChain, LlamaIndex, Haystack, and LangFlow.
  • Docling also offers an MCP server and an agent that can write, edit, extract, and enrich document content.
Source: UnlockBetterRAGAIAgentswithDocling

Chunkless RAG

Runtime

Keep the document tree and let an agent navigate titles, sections, paragraphs, tables, and images. It is strongest for long, organized documents where relationships across sections matter.

Best whenOne structured document needs precise, cross-section reasoning.
Not a replacementChunk search still fits millions of documents and fuzzy discovery.

A pragmatic combination: similarity search finds the document; structure navigation finds the answer inside it. The trade-off is more model calls and more latency. Producing a clean, navigable document tree is “most of the engineering.”

Important distinctions

A document tree is not the same thing as a knowledge graph. Chunkless RAG follows author and document hierarchy; GraphRAG follows entities and their relationships.
Chunkless does not mean retrieval-free or context-unlimited. It navigates preserved document structure and selects relevant sections instead of relying on a flat chunk index.
Source: WhatIsChunklessRAGHowDoclingAIAgentsNavigateDocuments

Integration + governance

Index time

Repeatable pipelines connect unstructured sources, extract text, deduplicate, annotate language, remove PII, chunk, embed, and load only deltas. Native ACLs preserve document-level permissions.

Governance then adds entities, classification, quality checks, contextual metadata, validation rules, a central catalog, and lineage.

Enterprise claim in the source: over 90% of enterprise data is unstructured, while under 1% reaches generative-AI projects.
Source: UnlockingSmarterAIAgentswithUnstructuredDataRAGVectorDatabases

Why complex-document RAG fails

Architecture
AmbiguityOne corpus can contain multiple correct answers because the question leaves time or scope unstated.
ContradictionOld and new policy, federal and state rules, or multiple authors can disagree.

Fix unforced data errors, ask clarifying questions, and keep the answer “less than or equal to the data”: if the corpus admits X, Y, or Z, present all three with context rather than collapsing uncertainty into one claim. Presenting a legal opinion as settled fact is a design error, not a hallucination.

03

Retrieve evidence

Retrieval begins with lexical and semantic recall, then adds query transformation, fusion, and re-ranking to raise precision without flooding the model.

Sparse retrieval

Query time

TF-IDF and BM25 score exact terms over an inverted index. It is cheap, scalable, and strong for code, logs, legal clauses, and rare domain terms. BM25 can outperform neural methods on domain-specific terms.

WinsExact wording.
MissesSynonyms and paraphrase.
Source: Top3RAGRetrievalStrategiesSparseDenseHybridExplained

Dense retrieval

Query time

Embedding models map queries and documents into a shared vector space; ANN or kNN ranks semantic similarity. Strong for natural-language variation and unstructured knowledge.

WinsMeaning across different words.
MissesRare jargon and very short queries.
Source: Top3RAGRetrievalStrategiesSparseDenseHybridExplained

Hybrid retrieval

Query time

Run semantic and keyword retrieval in parallel, then fuse the lists with a weighted sum (example: 70% dense / 30% sparse) or reciprocal rank fusion.

Why it winsSemantic recall plus exact-term precision.
Source verdictThe default for serious RAG deployments.

Important distinctions

Qualify the word “hybrid”: distinguish sparse + dense hybrid retrieval from hybrid chunking, text retrieval with original-media generation, and RAG + CAG combinations. The sources use “hybrid” in all these senses.
Source: Top3RAGRetrievalStrategiesSparseDenseHybridExplained

Re-ranking

Query time

Retrieve broadly, then use a specialized model, often a cross-encoder, to reduce 20–50 candidates to the most relevant few. This considers more knowledge without forcing all of it into the LLM.

Source recommendation: the first strategy to add for almost every RAG implementation; a second model raises cost slightly.
Sources: EveryRAGStrategyExplainedin13MinutesNoFluff; RAGvsAgenticAIHow LLMsConnectDataforSmarterAI

Query transformation

Query time

Expansion rewrites one query with useful detail. Multi-query RAG generates several variants and searches them in parallel for broader coverage.

GainPrecision or coverage.
CostAn extra LLM call; multi-query also adds database searches.
Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Self-reflective RAG

Runtime

Search, have an LLM grade the retrieved chunks against the question (for example, 1–5), then retry with a refined query below a threshold (for example, under 3).

GainA simple correction loop.
CostGrading every search and possible retries.
Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Fine-tuned embeddings

Index timeQuery time

Train the embedding model on a domain dataset, then use it for both indexing and queries. The source cites 5–10% accuracy gains and notes that a small specialized model can beat a larger generic one on its target task.

Constraint: requires substantial training data and ongoing infrastructure; strongest when a trainable domain dataset exists. The talk’s sentiment example aligns “my order was late” with “items are always sold out” because both express negative sentiment despite different vocabulary.
Source: EveryRAGStrategyExplainedin13MinutesNoFluff

Architecture

Candidate search and storage tools named across the collection include Elasticsearch, Lucene, Milvus, JVector, Weaviate, Astra DB, and pgvector.

Expand the substrate

Text chunks in one vector index are only the baseline. Richer RAG adds native media, graph relationships, and agents that choose how,and whether,to retrieve.

Multimodal RAG: three levels

Architecture
LevelMechanismTrade-off
1 · Text-ify everythingCaption images; transcribe audio/video; run normal text RAG.Simple, but captions lose visual nuance.
2 · Hybrid multimodalRetrieve text captions/transcripts, then pass the linked original artifact to a multimodal LLM.The model sees the real media, but retrieval is only as good as its text surrogate.
3 · Full multimodalAligned text, image, and audio encoders share one vector space; retrieve every modality directly.Richest grounding; stronger encoders, more compute, and careful context summarization.

Important distinctions

Multimodal describes the handling of media, not an orchestration policy. Record both retrieval modality and generator input modality.

GraphRAG

Architecture

Combine a graph of entity relationships with vector search. The graph scopes the question,what is connected to this entity and which documents relate,while vectors fill in detail within that scope.

Best whenData is highly interconnected.
CostLLM-based graph construction is slow and expensive.
Coverage caveat: GraphRAG appears briefly in two source talks; no Neptune, Microsoft GraphRAG, or implementation deep dive is present.
Sources: EveryRAGStrategyExplainedin13MinutesNoFluff; HowRAGGraphRAGandContextEngineeringImproveAIPerformance

Agentic RAG

Runtime

Retrieval becomes a tool inside a reasoning loop. The agent can choose semantic search, inspect a whole document, switch knowledge bases, call an external service, retry, use an off-topic fallback, or decide it has enough. It can also select an output format such as text, chart, or code.

Best whenQuestions need adaptive, multi-step evidence gathering.
Trade-offMaximum flexibility, lower predictability; routing instructions must be clear.

Important distinctions

Agentic RAG describes control flow; GraphRAG describes relationship-oriented representation and retrieval. Neither excludes the other.
Sources: EveryRAGStrategyExplainedin13MinutesNoFluff; WhatisAgenticRAG; RAGsEvolutionFromSimpleRetrievaltoAgenticAI

Context engineering

Runtime

The talks use “context engineering” in three related ways: as the broad discipline of giving a model the right information, as a data architecture spanning access and governance, and as online prompt assembly or compression. Four pillars recur:

  • Connected access: query data where it lives.
  • Knowledge layer: resolve entities, relationships, hierarchies, and decision traces.
  • Precision retrieval: filter by intent, role, time, and policy.
  • Runtime governance: enforce access during retrieval and response.

This page uses context assembly for the narrower online step of selecting, ranking, merging, and compressing evidence for the generator.

Sources: HowRAGGraphRAGandContextEngineeringImproveAIPerformance; RAGvsAgenticAIHow LLMsConnectDataforSmarterAI

Choose the architecture

RAG is one way to put knowledge into a model’s working context. Choose it by data shape, freshness, scale, latency, and whether the system must know, act, remember, or follow a procedure.

PatternChoose whenWatch for
RAGKnowledge is large, dynamic, proprietary, or needs citations.Retrieval can silently miss what exists.
Long contextA bounded corpus needs global reasoning, such as one contract or book.Re-reading cost and attention dilution on very long inputs.
CAGA fixed corpus fits the window, latency matters, and the cache changes rarely.The talk cites typical 32–100K-token windows, a possibly dated range; every knowledge change requires cache recomputation.
Fine-tuning / LoRAA specific behavior bottleneck remains after prompting, RAG, and skills; or latency demands a smaller model.Weights are not a convenient store for fresh facts.
MCPThe model must discover and call live tools or systems.It complements RAG; it does not replace grounded document knowledge.
Agent skillThe system needs a repeatable procedure plus judgment, loaded on demand.Procedural knowledge is different from facts.
MemoryThe agent should reuse experience it recorded from prior work.Provenance differs: memory is agent-written; RAG is human-curated.
ADKThe AI must execute multi-step workflows and use tools consistently.Most production systems pair action (ADK) with knowledge (RAG).

RAG vs long context

Architecture

Long context wins by collapsing the stack, removing the retrieval lottery, and supporting whole-book comparisons, including finding what is missing.

RAG wins by avoiding the re-reading tax. The talk equates a 500-page manual to about 250K tokens and uses a 500K-token haystack example; these talk-stated context-window figures may date quickly. Prompt caching only partly offsets the cost of repeatedly reading long inputs.

Sources: IsRAGStillNeededChoosingtheBestApproachforLLMs; RAGvsAgenticAIHow LLMsConnectDataforSmarterAI

RAG vs CAG

Architecture

CAG loads the entire knowledge base once and reuses the transformer’s key-value cache. It offers one-forward-pass latency, but the model must extract the right answer from everything present.

Hybrid: let RAG retrieve a relevant subset, then cache it as working memory for follow-up questions.

Source: RAGvsCAGSolvingKnowledgeGapsinAIModels

RAG before fine-tuning

Architecture

The source’s no-weights stack is: base model → prompt/context engineering → RAG for fresh or proprietary knowledge → skills for procedure → fine-tuning for a remaining bottleneck, usually with LoRA.

The case for default fine-tuning weakened as context windows passed 1M tokens, reasoning models improved, and frontier models caught up. One 2023 legal fine-tune preferred 97% over GPT-4 was surpassed by seven general models on the company’s 2025 benchmark.

Fine-tuning still fits: latency-critical voice systems, distillation, and reinforcement fine-tuning when outputs can be graded programmatically.
Source: IsFineTuningStillNeededLLMsRAGLoRA

RAG + MCP

Runtime

A useful but simplified split is that RAG often supplies knowledge while MCP exposes capabilities. In practice the boundary overlaps: an MCP server can expose search to agents, and an agent can use RAG as a tool. MCP follows discover → understand → plan → execute → integrate; a well-designed agent decides when to retrieve documents and when to call other tools.

Source: MCPvsRAGHowAIAgentsLLMsConnecttoData

Measure & operate

A RAG system is only trustworthy when its answer, evidence, safety, and behavior can be measured,and when the deployment path keeps those checks visible.

Seven model-risk measurements

Runtime
ROUGERecall and completeness via word-sequence overlap with an expected answer; 0–1.
BLEUPrecision of generated words against expected text; penalizes longer responses.
METEORAn average of precision and recall for a rounded overall score.
PIIWhether names, email addresses, phone numbers, or other identifiers leak in or out.
HAPHate, abuse, and profanity monitoring.
Context relevanceWhether an answer,correct or not,actually addresses the question asked.
HallucinationIncorrect answers presented as correct.
Coverage gap: the transcripts do not discuss retrieval metrics such as recall@k, MRR, or nDCG, nor RAGAS-style faithfulness or answer-relevance frameworks.
Interpretive safeguards
  • Keep retrieved-context relevance separate from answer relevance; the source material mixes the two, so do not treat its labels as a precise metric specification.
  • ROUGE, BLEU, and METEOR are reference-answer comparison metrics, not proof that an answer is grounded, safe, or correct.
  • Separate three failure types when classifying failures: a missing retrieval result, an unsupported answer, and contradictory source material.
  • Treat document version and applicability as metadata and governance concerns.
